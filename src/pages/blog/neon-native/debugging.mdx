## LogBox: the yellow/red boxes

In development, errors and warnings appear as red/yellow overlays. Read them — they're usually
accurate and point at the exact line.

- **Red** = error (usually crashes the render).
- **Yellow** = warning (won't crash now, might later — e.g. deprecated prop).

Dismiss a warning with the `X`, or ignore the whole box for the session. Don't ship with
warnings — fix them or add a justified `// eslint-disable`.

## React DevTools

Open the in-app dev menu (shake the phone or press `m` in the terminal), tap "Open React
DevTools". Inspect the component tree, see props/state, and — critically — see **what
re-renders** (highlight updates). This is your #1 tool for finding unnecessary renders.

## ErrorBoundary: catch render crashes

A render error unmounts the whole tree — white screen. An ErrorBoundary catches it and shows
a fallback:

```tsx
import React from 'react';

class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error(error, info);
    // also: Sentry.captureException(error)
  }
  render() {
    if (this.state.hasError) {
      return <FallbackScreen onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}
```

Wrap your app's root — and wrap **individual feature screens** so one broken screen doesn't
white-out the whole app.

## Sentry: production crash reporting

Expo has a first-party Sentry integration:

```bash
npx expo install @sentry/react-native
npx expo install expo-dev-client   # Sentry needs a dev build
```

```tsx
import * as Sentry from '@sentry/react-native';

Sentry.init({
  dsn: 'https://...@...ingest.sentry.io/...',
  tracesSampleRate: 0.2,
});
```

Now every uncaught error and native crash reports to your Sentry dashboard with stack trace,
device, OS version, and breadcrumbs. You'll know about crashes before your users do.

## console.log vs the debugger

- `console.log` — quick, fine for one-off checks. Remove before shipping (it leaks data and slows the JS thread).
- **Breakpoints** in VS Code (Expo Tools) — pause and inspect, far more powerful.
- `react-native-logs` — structured logging with levels, better than scattered `console.log`.

<Pitfall title="console.log in production">
  Every log line is a synchronous JS-thread call in production too. A hot path full of
  <code>console.log</code> visibly drops frames, and it can leak PII into device logs. Strip
  or gate logs behind <code>__DEV__</code>.
</Pitfall>
